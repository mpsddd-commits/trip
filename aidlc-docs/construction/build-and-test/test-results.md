## 2. 🔴 발견한 실제 결함 6건

### 결함 1 — 로그 한 줄이 요청을 죽인다 (C2, SEC-03)

`SensitiveFilter` 가 **모든** 로그 인자를 `str()` 로 바꿔 마스킹했다.
그 결과 `%d` · `%f` 를 쓰는 로그가 `TypeError` 를 냈다.

문제는 **예외가 삼켜지지 않는다**는 것이다. `logging.Filter` 는 `Handler.emit()` 의
try/except **밖**에서 실행되므로, 예외가 로그를 호출한 코드까지 그대로 올라간다.
httpx 가 요청마다 `'HTTP Request: %s %s "%s %d %s"'` 를 남기므로
**사실상 모든 API 호출이 예외로 끝났다.**

- **영향**: 운영에서 전 API 500. u1 테스트 35건 이상이 이것 하나로 실패했다.
- **조치**: 문자열 인자만 마스킹하고 다른 형은 보존. 최종 마스킹은 `JsonFormatter` 가
  포맷을 마친 메시지에 한 번 더 적용(이중 방어). 회귀 테스트 11건 추가.

### 결함 2 — 캐시를 읽을 때마다 예외 (C12, NFR-4)

`CacheRepository.get()` 이 `row.expires_at <= utcnow()` 를 비교했는데,
**SQLite 는 타임존을 저장하지 않는다.** 컬럼을 `DateTime(timezone=True)` 로 선언해도
SQLAlchemy 가 돌려주는 값은 naive 이고 `utcnow()` 는 aware 라
`TypeError: can't compare offset-naive and offset-aware datetimes` 가 났다.

- **영향**: 외부 API 캐시가 통째로 동작 불가. **쓰기는 성공하므로 증상이 늦게 드러난다.**
  캐시 미스가 아니라 예외이므로 호출 경로가 500 으로 끝난다.
- **조치**: 읽을 때 naive 값에 UTC 를 붙인다 (`_as_utc`).

### 결함 3 — 2개짜리 하루는 절대 재정렬되지 않는다 (C18, BR-20)

`optimize()` 가 `len(items) <= 2` 에서 입력 순서를 그대로 반환했다.
이동 시간 행렬은 **비대칭**(일방통행·대중교통 방향별 배차)이므로
항목이 둘뿐이어도 뒤집는 편이 빠를 수 있다.

- **영향**: 조용히 최적이 아닌 답. P-08(비악화)은 만족하므로 **어떤 오류도 나지 않는다.**
- **발견 경로**: PBT P-09 의 완전탐색 오라클 비교. 이것이 없었으면 못 잡았다.
- **조치**: `len(items) <= 1` 로 변경 → n=2 는 완전탐색이 처리한다.

### 결함 4 — 입력한 영업시간이 사라진다 (FR-13, BR-35)

`PUT /api/trips/{id}/items/{item_id}/opening-hours` 가 200 을 돌려주는데
값이 저장되지 않았다. 영업시간은 **별도 테이블**인데 저장 경로가
`place_to_row()` 만 병합하고 `opening_hours_to_row()` 를 부르지 않았다.
(그 함수는 작성돼 있었지만 **아무도 호출하지 않는 죽은 코드**였다.)

- **영향**: 사용자가 영업시간을 입력하고 성공 메시지를 받은 뒤, 다음 조회에서 사라진다.
  FR-13 이 통째로 무력.
- **조치**: 저장 경로에 병합 추가. **컨테이너에서 실제 API 로 왕복 확인**했다.

### 결함 5 — `.env` 없이는 기동 자체가 실패 (FR-33, I-10)

`docker-compose.yml` 의 `env_file: [.env]` 는 파일이 없으면 **컴포즈가 즉시 죽는다.**
그런데 FR-33 과 README 의 첫 실행 안내는 "자격증명 없이 목 모드로 시작"이다.

- **영향**: 문서대로 따라 한 사용자가 첫 명령에서 막힌다.
- **조치**: `env_file: [{path: .env, required: false}]`.

### 결함 6 — 마스킹이 정작 토큰을 남긴다 (SEC-03)

두 가지 구멍이 있었다.
1. `Authorization: Bearer <토큰>` — 패턴이 값으로 **"Bearer"** 를 잡아 가리고
   **정작 토큰은 그대로 로그에 남겼다.**
2. `{'api_key': 'value'}` — 파이썬 repr/JSON 형태(키 뒤에 따옴표)를 인식하지 못했다.
   딕셔너리를 `%s` 로 로깅하면 정확히 이 형태가 된다.

- **조치**: 두 형태를 모두 잡도록 패턴 개정, `client_id`·`access_token`·`password` 추가.

## 3. 수정한 테스트 결함 6건

**코드가 아니라 테스트가 틀린 경우도 같은 무게로 다뤘습니다.** 통과시키려고 기대값만
바꾼 것이 아니라, 왜 원래 주장이 성립하지 않는지를 각 파일에 적었습니다.

| # | 테스트 | 무엇이 틀렸나 |
|---|---|---|
| 1 | `test_minimum_durations_for_close_points` | BR-25 는 `거리÷속도 + 600초(대기)`, 최소 600. **대기가 더해지므로** 거리가 0 이 아니면 항상 600 을 넘는다. 12m → 602. 테스트는 최소값이 지배할 것이라 잘못 가정했다 |
| 2 | `test_p21_whitespace_and_case_variants_share_a_key` | 임의 유니코드를 생성했다. `'ı'.upper()=='I'`, `'ß'.upper()=='SS'` 처럼 **대문자화는 되돌릴 수 없다.** 결과는 캐시 미스일 뿐 오답이 아니므로, 실제 질의 문자 집합(한글·영문·숫자)으로 좁혔다 |
| 3 | `test_p22_nearby_coordinates_share_a_key` | 좌표를 밀다가 **국내 범위 밖으로 나가** 도메인 검증이 돌았다. 또 임의의 두 값은 1e-7 차이라도 반올림 경계를 사이에 둘 수 있다 — 모든 양자화의 성질이다. 속성을 **격자점 기준**으로 다시 세웠다 |
| 4 | `test_p22_distant_coordinates_get_different_keys` | 경계에서 잘리면 실제 이동량이 1m 미만이 될 수 있는데(38.999999999 → 39.0), 그때 같은 키가 나오는 것이 정상이다. 전제가 성립할 때만 주장하도록 고쳤다 |
| 5 | `test_p19_ics_roundtrip_preserves_documented_fields` | RFC 5545 의 TEXT 값은 **단독 CR 을 담을 방법이 없다.** `\r` → `\n` 정규화가 규격에 맞는 동작이므로, 줄바꿈 정규화 후 비교하도록 바꿨다 |
| 6 | `test_response_body_contains_no_secret_markers` | 응답에서 `"anthropic"` 이라는 **벤더 이름**을 찾아 실패했다. 그런데 `modes` 는 FR-33 이 요구하는 필드로 `{"anthropic":"mock"}` 처럼 어떤 기능이 데모인지 알린다 — 비밀이 아니다. 가짜 자격증명을 주입하고 그 **값**이 본문에 없는지 보도록 다시 썼다 |

## 7. 이번 실행에서 배운 것

1. **광범위한 실패는 원인이 하나인 경우가 많다.** 35건이 로그 필터 한 줄 때문이었다.
2. **PBT 는 예제 테스트가 못 잡는 것을 잡는다.** 최적화기의 n=2 결함은
   완전탐색 오라클 비교로만 드러났다. 어떤 예외도 나지 않는 종류의 버그다.
3. **"200 을 돌려준다"가 "저장됐다"는 뜻이 아니다.** 영업시간 결함은
   엔드포인트 테스트가 응답만 보고 재조회를 하지 않았다면 영원히 숨어 있었다.
4. **속성이 틀릴 수도 있다.** 실패한 속성 5건 중 4건은 코드가 아니라 속성의 과잉 주장이었다.
   통과시키려 기대값을 바꾸는 것과, 왜 성립하지 않는지 이해하고 다시 세우는 것은 다르다.
