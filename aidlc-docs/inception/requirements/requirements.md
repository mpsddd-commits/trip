## 3. 모순·모호성 분석 결과

전체 답변에 대해 교차 검증을 수행했습니다. **8건**의 충돌·모호성을 발견했으며, 전부 **설계로 해결 가능**하여 추가 질문 없이 아래와 같이 해소합니다. 이견이 있으시면 승인 게이트에서 "Request Changes"로 알려주세요.

### CA-1 🔴 (중대) Q12(안드로이드 WebView) ↔ Q20(127.0.0.1 루프백 바인딩)
**충돌**: 안드로이드 기기·에뮬레이터에서 개발 PC의 `127.0.0.1` 은 **접근 불가능**합니다(에뮬레이터는 `10.0.2.2`, 실기기는 LAN IP 필요). 루프백 전용 바인딩을 그대로 두면 WebView 앱이 서버에 전혀 접속하지 못합니다.
**해소**: 서버 바인딩 호스트를 `.env` 의 `BIND_HOST` 로 분리(기본 `127.0.0.1`, 안드로이드 연동 시 `0.0.0.0`), 안드로이드 앱의 접속 주소를 `BuildConfig.BASE_URL` 로 주입해 빌드 변형(debug/release)마다 다르게 설정. → **FR-26, NFR-14, CON-4**

### CA-2 🟠 Q16(인증 없음) ↔ SECURITY-08(deny by default) / SECURITY-12(인증)
**충돌**: 보안 확장은 모든 엔드포인트에 인증을 요구하지만 Q16은 로그인 없음을 선택했습니다.
**해소**: 사용자 계정 개념이 없으므로 SECURITY-12는 **N/A**. SECURITY-08은 "모든 경로를 명시적 public 으로 선언"하고, 대신 **자원 식별자 추측 불가능성**(UUIDv4)과 **열거 방지**로 IDOR을 차단합니다. → **SEC-08, FR-24**

### CA-3 🟠 Q16(인증 없음) ↔ Q18(공유 링크)
**모호성**: Q16=A(익명 저장)와 Q18=A(공유 링크)의 조합은 사실상 Q16의 D 옵션("익명 + 비밀 링크")과 동일합니다.
**해소**: 로그인은 없고, 일정은 **추측 불가능한 UUIDv4 식별자**로 접근합니다. 공유 링크는 별도의 **읽기 전용 토큰**을 사용해 편집 권한과 분리합니다. → **FR-24**

### CA-4 🟠 Q20(로컬 HTTP) ↔ SECURITY-01(전송 중 암호화) / SECURITY-04(HSTS)
**충돌**: 루프백 HTTP 배포에는 TLS가 없어 TLS 1.2+ 강제와 HSTS가 성립하지 않습니다.
**해소**: **문서화된 예외**로 처리합니다. 애플리케이션은 보안 헤더를 항상 설정하되 HSTS는 HTTPS 요청에서만 전송하고, 외부 API 호출(NCP·네이버·Anthropic)은 전부 TLS 1.2+ 강제 — 즉 **외부 구간은 완전 준수, 루프백 구간만 예외**. 클라우드 배포 시 리버스 프록시 TLS 종단이 필요함을 배포 문서에 명시. → **SEC-01, SEC-04, CON-5**

### CA-5 🟡 Q16(인증 없음) ↔ Q4(Claude API 유료 호출)
**리스크**: 인증 없는 공개 엔드포인트가 유료 LLM을 호출하면 비용 남용에 노출됩니다.
**해소**: SECURITY-11에 따라 LLM·외부 API 호출 엔드포인트에 **레이트 리밋 + 일일 호출 상한**을 필수 적용. → **SEC-11, NFR-4**

### CA-6 🟡 Q19(부분 오프라인) ↔ Q17(서버 SQLite)
**모호성**: 오프라인 조회를 하려면 클라이언트 측 저장이 필요합니다.
**해소**: **서버 SQLite가 원본(source of truth)**, 클라이언트 IndexedDB는 **읽기 전용 캐시**. 오프라인 중 편집은 차단하고 안내 배너를 표시합니다(양방향 동기화·충돌 해결은 범위 제외). → **FR-29, FR-30, OUT-6**

### CA-7 🟡 SECURITY-02·06·07·14 ↔ 로컬 단독 배포
**충돌**: 로드밸런서·API 게이트웨이·CDN·IAM·VPC·중앙 로그 서비스가 존재하지 않습니다.
**해소**: SECURITY-02·06·07은 **N/A**(해당 리소스 없음). SECURITY-14는 **로컬 파일 기반 감사 로그 + 90일 로테이션 + 보안 이벤트 로그 레벨 분리**로 축소 적용합니다. → **SEC-14**

### CA-8 🟡 Q22(단위 테스트 중심) ↔ PBT-08(CI 통합)
**충돌**: CI 파이프라인이 없는 로컬 프로젝트입니다.
**해소**: PBT는 시드 로깅과 재현 명령을 반드시 갖추고, **CI 설정 파일(GitHub Actions)은 산출물로 제공하되 실행은 사용자 재량**으로 둡니다. → **PBT-R4, CON-6**

## 6. 기능 요구사항 (Functional Requirements)

### 6.1 여행 생성 및 AI 일정 편성

- **FR-1** 사용자는 새 여행을 생성할 때 다음을 입력한다: 목적지(시/군/구 또는 지역명), 시작일·종료일, 동행 인원, 여행 스타일 태그(맛집/자연/역사/쇼핑/휴식/액티비티 등 복수 선택), 1일 활동 시작·종료 시각, 주 이동수단(도보·자동차·대중교통), 예산 수준(선택).
- **FR-2** 시스템은 FR-1 입력을 Claude API에 전달하여 **일자별 방문 장소 초안**을 생성한다. 응답에는 장소명, 카테고리, 권장 체류시간, 추천 사유, 권장 방문 시간대가 포함된다.
- **FR-3** 🔴 **그라운딩(필수)**: LLM이 생성한 장소명은 그대로 신뢰하지 않고 **네이버 지역검색 API로 조회하여 실제 좌표·도로명주소·카테고리·전화번호로 해석**한다. 해석에 실패한 장소는 일정에 넣지 않고 "확인 필요" 목록으로 분리해 사용자에게 노출한다.
- **FR-4** 사용자는 여행을 저장·목록 조회·이름 변경·삭제할 수 있다.
- **FR-5** 사용자는 일자별 항목을 추가·삭제하고 **드래그 앤 드롭으로 순서를 변경**할 수 있으며, 일자 간 이동도 가능하다.
- **FR-6** 사용자는 장소를 직접 검색해 일정에 담을 수 있다. 네이버 지역검색은 **1회 최대 5건**을 반환하므로 `start` 파라미터 기반 "더 보기" 페이징을 제공한다.
- **FR-7** 사용자는 각 항목의 도착 시각(자동/수동 고정), 체류시간, 메모를 편집할 수 있다.
- **FR-8** 사용자는 일자별 **"순서 최적화"**를 실행할 수 있다. 총 이동시간을 최소화하되, 숙소를 시작·종료 지점으로 고정하는 옵션과 시각이 고정된 항목(예약 등)을 제자리에 두는 제약을 지원한다.

### 6.2 시간표 (타임라인)

- **FR-9** 시스템은 일정 변경 시 타임라인을 자동 재계산해 표시한다. 각 행은 **도착시각–출발시각 · 장소명 · 체류시간 · 다음 장소까지의 이동수단/이동시간/거리 · 메모**를 포함한다.
- **FR-10** 이동시간 산출 규칙:
  - 자동차 → NCP **Directions 5** 호출 결과(`duration`, `distance`, `path`)
  - 도보 → 두 지점의 하버사인 거리 × 보정계수(기본 1.3) ÷ 보행속도(기본 4.5 km/h)
  - 대중교통 → **근사치**로 계산하고 UI에 "실제와 다를 수 있음" 배지를 표시(CA는 FR-12로 보완)
  - 동일 구간·동일 수단 결과는 캐시하여 재호출하지 않는다
- **FR-11** 사용자는 항목별 이동수단을 개별 지정할 수 있으며, 미지정 시 FR-1의 주 이동수단을 따른다.
- **FR-12** 대중교통 구간에는 **"네이버지도로 길찾기"** 버튼을 제공해 `nmap://route/public` 딥링크로 실제 대중교통 안내를 위임한다.
- **FR-13** ~~영업시간 정보를 확보한 장소에 대해~~ → **2026-08-13 u1 Functional Design 에서 축소 확정 (Q10=A)**: **네이버 지역검색 API 가 영업시간을 제공하지 않으므로**, 영업시간은 **사용자가 장소별로 직접 입력**하는 선택 항목으로 둔다. 입력된 장소에 한해 배정 도착 시각이 영업시간 밖이면 **경고 배지**를 표시하고, 미입력 장소는 경고하지 않는다(거짓 경고 방지). 외부 데이터로 자동 확보하지 않는다.

### 6.3 지도

- **FR-14** 웹 화면은 NCP **Web Dynamic Map** 으로 지도를 렌더링한다.
- **FR-15** 방문 순서를 **번호 마커(①②③…)**로 표시하고, **일자별로 서로 다른 색상**을 적용한다.
- **FR-16** 인접 항목 사이에 **경로 폴리라인**을 그린다. 자동차 구간은 Directions 응답의 실제 경로 좌표, 도보·대중교통 구간은 점선 직선으로 구분해 표시한다.
- **FR-17** 마커 클릭 시 **장소 상세 패널**을 열어 주소·전화·카테고리·추천 콘텐츠(FR-20)·사진(FR-21)·네이버지도 열기 버튼을 표시한다.
- **FR-18** 일자 필터(1일차만 / 전체 보기)를 제공하고, 선택된 일자에 맞춰 지도 뷰포트를 자동 조정한다.
- **FR-19** 지도와 타임라인은 **양방향 하이라이트** 된다(타임라인 항목 선택 → 해당 마커 강조, 마커 선택 → 타임라인 스크롤·강조).

### 6.4 장소 추천 콘텐츠

- **FR-20** 장소별 추천 콘텐츠를 생성한다. 음식점 카테고리는 **대표 메뉴**, 관광지 카테고리는 **관람 포인트**를 제시한다. 네이버 **블로그 검색** 결과를 근거로 Claude API가 요약하며, **근거 블로그 링크를 함께 노출**하고 요약은 "AI 요약" 으로 명시한다.
- **FR-21** 네이버 **이미지 검색**으로 장소 썸네일을 표시한다. 출처를 함께 표기하고, 로드 실패 시 플레이스홀더로 대체한다.
- **FR-22** 현재 일정 항목 주변의 **미포함 추천 장소**(반경 내 동일/연관 카테고리)를 제안하고, 클릭 한 번으로 일정에 추가할 수 있다.

### 6.5 네이버지도 앱 연계

- **FR-23** 장소 상세와 타임라인에서 네이버지도 앱 딥링크를 제공한다: 장소 보기(`nmap://place`), 길찾기(`nmap://route/public|car|walk`).
- **FR-24** 네이버지도 앱이 설치되어 있지 않은 경우 **`map.naver.com` 웹 URL로 폴백**한다.

### 6.6 공유 및 내보내기

- **FR-25** 여행마다 **UUIDv4 식별자**를 부여하고, 별도의 **읽기 전용 공유 토큰**으로 공유 링크를 생성한다. 공유 링크 접근자는 조회만 가능하며 편집·삭제할 수 없다. 사용자는 공유 토큰을 폐기(재발급)할 수 있다.
- **FR-26** 일정을 **iCalendar(`.ics`)** 파일로 내보낸다. 각 일정 항목이 하나의 VEVENT가 되며 시각·장소·주소·메모를 포함하고 시간대는 `Asia/Seoul` 로 고정한다.

### 6.7 안드로이드 애플리케이션

- **FR-27** Kotlin 기반 **WebView 래퍼 앱**을 제공한다. 접속 주소는 `BuildConfig.BASE_URL` 로 주입되며 debug(개발 서버)/release(운영 주소) 빌드 변형을 분리한다. **(CA-1 해소)**
- **FR-28** JavaScript ↔ 네이티브 **브리지**를 제공한다: 네이버지도 앱 인텐트 실행, 시스템 공유 시트 호출, 위치 권한 요청 및 현재 위치 전달.
- **FR-29** 하드웨어 뒤로가기 버튼은 WebView 히스토리를 우선 소비하고, 히스토리가 없을 때만 앱을 종료한다.
- **FR-30** 네트워크 단절 시 **오프라인 안내 화면**을 표시하고 재시도 버튼을 제공한다.

### 6.8 오프라인

- **FR-31** 저장된 여행의 **일정·시간표 텍스트**는 클라이언트 캐시(IndexedDB)에서 오프라인 조회할 수 있다. 지도·검색·AI 기능은 온라인 전용이며 오프라인 시 비활성 상태로 명확히 표시한다.
- **FR-32** 오프라인 상태에서는 편집을 차단하고 안내 배너를 노출한다. 온라인 복귀 시 서버 데이터를 다시 내려받아 캐시를 갱신한다(서버가 항상 우선). **(CA-6 해소)**

### 6.9 운영·폴백

- **FR-33** 외부 API 인증 정보가 설정되지 않은 경우 **목(mock) 데이터 모드**로 기동하여 전 화면이 동작하도록 한다. 화면 상단에 "데모 데이터" 배너를 표시한다. **(ASM-1~3 대비)**
- **FR-34** 헬스체크 엔드포인트를 제공하고, 외부 API별 **일일 호출량 카운터**를 기록·조회할 수 있게 한다.

## 13. 요약

- **기능 요구사항 34건 / 비기능 요구사항 15건 / 보안 요구사항 15건 / PBT 요구사항 8건 / 제약 8건 / 범위 제외 10건 / 성공 기준 10건**
- **가장 중요한 설계 결정 3가지**:
  1. **대중교통 경로는 네이버 API로 계산 불가** → 앱 내부는 근사치, 실제 안내는 `nmap://` 딥링크 위임 (CON-1, FR-12)
  2. **LLM 출력은 반드시 네이버 지역검색으로 그라운딩** → 존재하지 않는 장소·폐업 정보가 일정에 들어가지 않게 차단 (FR-3, CON-7)
  3. **안드로이드 접속 주소는 빌드 설정으로 주입** → 루프백 바인딩과 WebView 접근성 충돌 해소 (CA-1, FR-27, NFR-14)
- **미확정 4건(ASM-1~4)** 은 전부 "폴백으로 흡수" 되도록 설계되어 재작업 위험이 없습니다.
